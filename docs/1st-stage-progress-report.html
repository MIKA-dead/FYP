a. Objectives of the Project

Creating high-quality character animation is still slow and expensive. Manual keyframing takes hours; motion capture needs costly hardware and heavy cleanup. For small studios and independent creators, the barrier is often time and skill, not creativity.

This project asks: what if creating animation were as easy as describing what you want? A user could say “a character jumps forward while raising both arms” and receive a usable motion file in minutes. The goal is not to replace animators, but to give them a collaborator for repetitive work so they can focus on storytelling.

Overall objective. Build an AI-powered animation assistant that turns plain-language descriptions (and later video or reference images) into editable motion, without manual keyframing or motion-capture cleanup.

End-of-project deliverables:

1. For animators: a practical tool that generates motion from text (and later video), with research-format outputs (.npy) and a clear path to industry formats (BVH / FBX / GLB).

2. For developers: a modular agent harness showing how an LLM can coordinate specialized sub-agents.

3. For research: a validated evaluation pipeline using motion speed magnitude (mean joint velocity) as a robust, data-driven quality signal.

Success criteria on real tasks (jump, walk, and combined actions): the result matches the user’s description, passes quality checks, and the full pipeline finishes in one session.

b. Proposed Solution or Changes Made

Original proposal. A motion-generation agent on a Model + Harness design: OpenCode + DeepSeek as the planner; sub-agents for motion synthesis, style transfer, and timeline editing; inputs of text, video, and motion clips; outputs of FBX/GLB with editable timeline metadata.

Changes made:

1. Dataset choice. Direct use of HumanML3D was delayed by AMASS licensing. The pipeline was first built on KIT-ML (7,813 samples, 251-dim) for rapid prototyping, and the feature path was then aligned toward a HumanML3D-style 263-dim representation for later model integration.

2. Evaluation metric. FID and user studies remain planned for Phase 4. In Phase 1, motion speed magnitude separated action types more clearly (for example RUN ≈ 38.5 versus WALK ≈ 20.1) and exposed intensity failures, so it became the core automated metric.

3. Generation backend. motion-coder currently uses a rule-based / simulated generator that edits base clips under hard constraints. This validates the harness and the evaluator before a real text-to-motion model is connected. The next attempt is Kimodo (NVIDIA’s kinematic motion diffusion model). MDM and MotionDiffuse remain alternative candidates.

4. Output format. Current outputs are .npy files in KIT-ML feature space. FBX/GLB export, and broader DCC or engine import, is deferred to Phase 3.

Solution implemented so far. A four-layer multi-agent system:

d. Problems Encountered

1. Generation is still simulated, not model-driven. Rule-based clip editing validates the harness, but it limits diversity and the response to novel prompts. Connecting a real text-to-motion model is the main technical risk of the next phase.

2. Prompt parsing is only partly reliable. A heuristic Intent Schema and router already cover coarse actions and revision types (texture, motion, key pose, and speed). Fine phrases such as “occasional right-hand wave” or “small mouth opening, calm expression” are not yet mapped to modules in a stable way, and the routed modules are still mocks.

3. Action modules are ordered incorrectly on long prompts with several consecutive actions. When one prompt contains a sequence—for example stand and smile, then walk two steps, then stop and hold the hands, then speak—the planner can select the relevant modules and still schedule them in the wrong order, so a later action is planned before an earlier one. This is a sequencing failure in the task graph, distinct from omitting a module. It appears on long, interleaved scripts and has to be fixed before routing results can be trusted on the target use case.

4. The evaluation metric has limited coverage. Speed magnitude separates WALK, RUN, and JUMP and detects weak motion intensity. It does not capture style (“heavy” versus “sneaky”), temporal edits, foot sliding, or physical issues such as penetration.

5. The knowledge base is action-centric and built from KIT-ML. It gives strong statistical baselines for coarse classes, and little guidance for style attributes such as tempo, amplitude, or “professional / calm”.

6. Multi-agent coordination propagates errors and hits context limits. A planner mistake can still look internally consistent to a speed-only tester. Long prompts and long reports consume the context window, force compaction, and can drop constraints.

7. The output format is not yet industry-ready. .npy suits research and internal scoring. Import into Unity, Unreal, Blender, or Maya needs a later FBX/GLB or BVH export.

MDM and MotionDiffuse remain fallback options if the Kimodo integration does not fit the current feature pipeline.
